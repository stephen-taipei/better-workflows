Better WorkflowsのREADMEはランディングページであり、圧縮したリファレンスマニュアルではありません。その役割は、読者が次の五つの問いに順番に答えられるようにすることです。

1. これは何で、自分に向いているのか？
2. どのような問題を解決するのか？
3. なぜその主張を信頼すべきなのか？
4. 最初の成功までの最短経路は何か？
5. 次にどこへ進めばよいのか？

この指針は、リポジトリ内のすべてのREADMEについて、物語構成、視覚表現、ローカライズ、検証の規約を定義します。機械可読の原本は[`readme-quality-v1.json`](../../../plugins/better-workflows/config/readme-quality-v1.json)です。

## 読者の判断を出発点にする

GitHubは、リポジトリの大半のコンテンツより先にREADMEを表示します。そのため最初の画面では、製品が約束する価値、想定読者、範囲を限定した次の行動を明確にしなければなりません。内部アーキテクチャ、完全なコマンドリファレンス、リリース復旧の詳細から始めてはいけません。

次の読者の目的に合わせて書きます。

- **新規訪問者：** Better Workflows が関連する問題を解決できるかどうかを迅速に判断します。
- **新規ユーザー：** プラグインをインストールし、自動ルートを一つ正常に完了させます。
- **評価者：** 権限境界とフェイルクローズな動作を理解します。
- **リピーターのオペレーター：** ワークフロー、セキュリティ、アーキテクチャ、または CLI の回答にすばやく移動します。
- **コントリビューターまたは翻訳者：** 正式なコントラクト、開発コマンド、サポート、ガバナンスを確認します。

## 原因と結果に沿って語る

五つのランディングREADMEは、同じ八部構成の意味的な順序を使います。見出しは各言語で自然な表現にできますが、読者のたどる道筋は変わりません。

| セクション | 読者の問いと物語上の役割 |
| --- | --- |
| 約束と対象読者 | Better Workflowsとは何か、なぜ存在するのか、誰のためのものか？ |
| 問題から結果へ | 意図、権限、証拠、プロバイダーの結果を混同すると、何が問題になるのか？ |
| 裏付けと境界 | どの保証によって、提示された結果を信頼できるのか？ |
| 最初の成功 | インストールから結果までの、最短かつ完全な経路は何か？ |
| 次の経路を選ぶ | 読者の目標に合うワークフローや文書はどれか？ |
| ライフサイクル | 目標はどのように照合済みの完了に至るのか、または安全に停止するのか？ |
| 信頼と限界 | システムが決して推論、承認、主張してはならないことは何か？ |
| 学ぶ、助けを得る、貢献する | 詳細な文書、サポート、ガバナンス、開発、ライセンスはどこにあるか？ |

この順序によって、実用的な物語の流れが生まれます。

- **背景：** プロンプトに基づく作業は、権限や状態を証明しなくても意図を表現できます。
- **緊張：** 副作用によって、その隔たりが成果提供のリスクに変わります。
- **解決：** Better Workflowsは、目標、範囲、証拠、レビュー、行動、プロバイダーの結果との照合を結び付けます。
- **裏付け：** 明示的な保証と境界が、解決策の仕組みを示します。
- **行動：** 読者は、実装の深い詳細に触れる前に最初の成功に到達します。
- **継続：** 役割と結果に基づく経路が、読者を適切なチュートリアル、実践ガイド、解説、リファレンスへ導きます。

## ランディング内容と詳細文書を分ける

READMEには判断に関係する情報を載せます。目的に応じて詳細へ案内します。

- [はじめに](getting-started.md)は、初回利用のためのチュートリアルです。
- [ワークフロー](workflows.md)は、結果を選ぶための実践ガイドです。
- [アーキテクチャ](architecture.md)は、制御プレーンとトレードオフを説明します。
- [セキュリティ](security-guide.md)は、権限、プライバシー、アテステーション（検証証明）、未検証の場合に処理を拒否する動作を説明します。
- [CLIリファレンス](cli-reference.md)は、コマンドリファレンスです。
- ローカライズされた`docs/details/*.md`ページは、翻訳された詳細を網羅的に保持します。

キャッシュ復旧、ロックの所有権、プロバイダートランスポートの完全な意味論、網羅的なコマンド一覧、実装変更の履歴をランディングページに重複して載せないでください。簡潔な安全性の主張はそのページに残し、監査可能な詳しい裏付けは正本のガイドに置きます。

この分離は、チュートリアル、実践ガイド、解説、リファレンスを区別するDiátaxisに従っています。一つのページを、これら四つの読者のニーズすべてに同時に最適化することはできません。

## すべての視覚要素に置く理由を持たせる

視覚要素は、関係、階層、状態遷移を文章よりも実質的に理解しやすくできる場合にのみ使います。

ランディングページでは、二つの視覚要素を認めます。

1. **権限境界のアーキテクチャ：** どの層が意図、現時点の事実、ツールの権限、上限のある再試行、読み取り専用の状態を形作るのかに答えます。
2. **目標から完了までのライフサイクル：** どこで証拠を確認し、どこで副作用を承認し、どこで未知の状態によって進行が止まるのかに答えます。

すべての視覚要素に、次を含めなければなりません。

- 簡潔で意味のある代替テキスト。
- 視覚要素が非表示になったり、Mermaidが描画されなかったりしても結論を保持する、隣接した同等内容のテキスト。
- 可能な限り、重要なラベルに使う実際のテキスト。
- 視覚要素を最新に保つ理由となる、継続的に有効な読者の問い。

装飾用のスクリーンショット、文字の多い画像、短いリストを単に繰り返すだけの図を追加しないでください。選択用の表は簡潔な二列に抑え、幅の狭い画面でも使えるようにします。

## 言語が変わっても意味を保つ

英語は意味の参照基準であり、行数を合わせる目標ではありません。繁体字中国語、簡体字中国語、日本語、韓国語は、同じ規約を保ちながら、母語の読者に自然に読める必要があります。

次の項目は同等に保たなければなりません。

- 八つの意味的セクションとその順序。
- 最初の成功のためのコマンドと製品識別子。
- 権限、証拠、未知の状態、プロンプト、プライバシーに関する五つの主張。
- ワークフロー、セキュリティ、アーキテクチャ、CLI、サポート、ガバナンス、開発、ライセンスのリンク先。
- 視覚要素の目的、ライフサイクルの段階、代替テキスト。
- バージョンの参照元とバッジ方針。

見出し、文の区切り、句読点、例、行動を促す表現は、各言語に自然な形にできます。コマンド、セレクター、証拠識別子は翻訳せず、セキュリティ規則の意味も変えないでください。

## 拾い読みと翻訳に適した文章を書く

- 読者が得る結果を先に示し、重要な用語を見出しや段落の冒頭に置きます。
- 能動態を使い、行動の責任を負う主体を明示します。
- 手順では読者に直接語りかけます。
- 段落を短くし、それぞれに一つの役割を持たせます。
- 順序には番号付きリストを、順序のない選択肢には箇条書きを使います。
- 「ここをクリック」のような一般的なラベルではなく、内容を説明するリンクを使います。
- 見出しは階層的かつ具体的にし、同じ階層では並列した表現にします。
- 翻訳しても意味が保たれる、字義どおりで曖昧さのない表現を優先します。
- 条件は指示の前に、期待する結果はコマンドの後に置きます。

## 装飾ではなく意味を検証する

文書テストは、見出しの一致だけでなく、それ以上を検出しなければなりません。検証対象は次のとおりです。

- 一つの H1 と論理的な見出し階層；
- 順序付けられたセマンティックセクションと重要主張マーカー；
- 正確な初回成功コマンドと安定した識別子；
- 相対リンクとロケール固有の詳細リンク先；
- ランタイムメタデータと一致するバージョンバッジ；
- 意味のある画像の alt テキストと隣接する視覚的フォールバック；
- 完全なテキスト代替を備えた単一の Mermaid ライフサイクル；
- 二列の表と段落長の制限；
- ランディングページからの特定の詳細実装記述の排除；

## 調査の根拠

- [GitHub：リポジトリのREADMEファイルについて](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)は、初回訪問時のREADMEの目的を定義し、長い文書を別の場所に移すことを推奨しています。
- [Diátaxis](https://diataxis.fr/start-here/)は、チュートリアル、実践ガイド、解説、リファレンスのニーズを分けています。
- [Microsoft：拾い読みしやすいコンテンツ](https://learn.microsoft.com/en-us/style-guide/scannable-content/)は、重要なことを先に置く構成、短い段落、一貫した視覚的な入口を重視しています。
- [Googleの開発者向け文書スタイル](https://developers.google.com/style/highlights)は、能動態、直接の語りかけ、説明的な見出し、アクセシビリティ、世界中の読者に向けた文章を推奨しています。
- [GitHub：図の作成](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams)は、MarkdownでのMermaid対応を説明しています。
- [W3C WAI：画像チュートリアル](https://www.w3.org/WAI/tutorials/images/)は、情報を伝える視覚要素や複雑な視覚要素について、代替テキストと完全な同等説明を求めています。
