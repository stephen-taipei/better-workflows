[Обзор в 41 локализованной версии и официальные точки входа на сайте](../../../docs/LANGUAGES.md)\. Каноническим источником этой редакционной схемы остаётся английская версия\.

README проекта Better Workflows — это входная страница\, а не сжатый справочник\. Его задача — помочь читателю последовательно ответить на пять вопросов\:

1. Что это и подходит ли это мне\?
2. Какую проблему это решает\?
3. Почему я должен доверять этим утверждениям\?
4. Каков кратчайший путь к первому успеху\?
5. Куда мне двигаться дальше\?

Эта схема задаёт контракт повествования\, визуального представления\, локализации и проверки для каждого README репозитория\. Машиночитаемый источник — [`readme-quality-v1.json`](../../../plugins/better-workflows/config/readme-quality-v1.json)\.

## Начните с решения\, которое принимает читатель

GitHub показывает README раньше большей части содержимого репозитория\. Поэтому первый экран должен обозначить обещание продукта\, целевую аудиторию и следующий шаг с чёткими границами\. Он не должен начинаться с внутренней архитектуры\, полного справочника команд или подробностей восстановления выпусков\.

Пишите с учётом следующих задач читателей\:

- **Новый посетитель\:** быстро понять\, решает ли Better Workflows актуальную задачу\.
- **Новый пользователь\:** установить плагин и пройти один успешный автоматический маршрут\.
- **Оценщик\:** понять границы полномочий и поведение fail\-closed\.
- **Возвращающийся оператор\:** сразу перейти к ответу по workflow\, безопасности\, архитектуре или CLI\.
- **Контрибьютор или переводчик\:** найти канонический контракт\, команды разработки\, поддержку и управление проектом\.

## Стройте повествование на причинах и следствиях

Пять входных README используют одну и ту же смысловую последовательность из восьми частей\. Заголовки могут звучать естественно на каждом языке\, но путь читателя остаётся неизменным\.

| Раздел | Вопрос читателя и роль в повествовании |
| --- | --- |
| Обещание и аудитория | Что такое Better Workflows\, зачем он существует и для кого предназначен\? |
| От проблемы к результату | Что идёт не так\, когда смешивают намерение\, полномочия\, доказательства и результат провайдера\? |
| Подтверждения и границы | Какие гарантии делают предлагаемый результат заслуживающим доверия\? |
| Первый успех | Каков кратчайший полный путь от установки до результата\? |
| Выбор следующего пути | Какой рабочий процесс или документ соответствует цели читателя\? |
| Жизненный цикл | Как цель превращается в завершение со сверенными результатами — либо процесс безопасно останавливается\? |
| Доверие и ограничения | Что система никогда не вправе выводить\, разрешать или утверждать\? |
| Обучение\, помощь\, участие | Где находятся подробная документация\, поддержка\, правила управления\, материалы для разработки и лицензия\? |

Этот порядок создаёт практическую сюжетную линию\:

- **Контекст\:** работа по запросам к моделям может выражать намерение\, не доказывая полномочий или состояния\.
- **Напряжение\:** побочные эффекты превращают этот пробел в риск для получения результата\.
- **Решение\:** Better Workflows связывает цель\, границы задачи\, доказательства\, проверку\, действие и сверку с результатом провайдера\.
- **Подтверждение\:** явные гарантии и границы показывают\, как работает решение\.
- **Действие\:** читатель достигает первого успеха\, прежде чем сталкивается с подробными деталями реализации\.
- **Продолжение\:** маршруты по ролям и результатам направляют читателя к нужному учебному материалу\, практическому руководству\, объяснению или справочнику\.

## Отделяйте входную страницу от подробной документации

Используйте README для информации\, необходимой для принятия решения\. Направляйте к подробностям в зависимости от цели\:

- [Начало работы](getting-started.md) — учебный материал для первого использования\.
- [Рабочие процессы](workflows.md) — практическое руководство по выбору результата\.
- [Архитектура](architecture.md) объясняет плоскость управления и компромиссы\.
- [Безопасность](security-guide.md) объясняет полномочия\, конфиденциальность\, аттестации и блокировку действий при отсутствии подтверждения\.
- [Справочник CLI](cli-reference.md) служит справочником команд\.
- Локализованные страницы `docs/details/*.md` сохраняют полные переведённые подробности\.

Не дублируйте на входной странице восстановление кеша\, владение блокировками\, полную семантику транспорта провайдеров\, исчерпывающий перечень команд или историю изменений реализации\. Краткое утверждение о безопасности остаётся на странице\; подробности\, позволяющие его проверить\, относятся к каноническому руководству\.

Это разделение следует принятому в Diátaxis различию между учебными материалами\, практическими руководствами\, объяснениями и справочниками\. Одну страницу невозможно оптимизировать для всех четырёх потребностей читателя одновременно\.

## Обосновывайте место каждого визуального элемента

Используйте визуальный элемент\, только если он существенно облегчает понимание связей\, иерархии или переходов между состояниями по сравнению с текстом\.

На входных страницах допускаются два визуальных элемента\:

1. **Архитектура границ полномочий\:** отвечает на вопрос\, какие слои формируют намерение\, текущие факты\, полномочия инструментов\, ограниченные повторные попытки и состояние только для чтения\.
2. **Жизненный цикл от цели до завершения\:** отвечает на вопросы\, где проверяют доказательства\, где разрешают побочные эффекты и где неизвестное состояние останавливает продвижение\.

Каждый визуальный элемент должен включать\:

- краткий\, содержательный альтернативный текст\;
- расположенный рядом текстовый эквивалент\, сохраняющий вывод\, когда визуальный элемент скрыт или Mermaid не отображается\;
- настоящий текст для существенных подписей\, когда это возможно\;
- устойчивый вопрос читателя\, оправдывающий поддержание визуального элемента в актуальном состоянии\.

Не добавляйте декоративные снимки экрана\, изображения с большим объёмом текста или диаграмму\, которая лишь повторяет короткий список\. Ограничивайте таблицы выбора двумя лаконичными столбцами\, чтобы они оставались удобными на узких экранах\.

## Сохраняйте смысл при переводе

Английский служит смысловым эталоном\, а не ориентиром по количеству строк\. Традиционный китайский\, упрощённый китайский\, японский и корейский должны звучать естественно для носителя языка\, сохраняя при этом тот же контракт\.

Следующие элементы должны оставаться эквивалентными\:

- восемь смысловых разделов и их порядок\;
- команды для первого успеха и идентификаторы продуктов\;
- пять утверждений о полномочиях\, доказательствах\, неизвестном состоянии\, запросах к моделям и конфиденциальности\;
- целевые страницы рабочих процессов\, безопасности\, архитектуры\, CLI\, поддержки\, управления\, разработки и лицензии\;
- назначение визуальных элементов\, этапы жизненного цикла и текстовые замены\;
- источник версии и правила для значков\.

Заголовки\, границы предложений\, пунктуация\, примеры и призывы к действию могут быть естественными для языка\. Никогда не переводите команды\, селекторы\, идентификаторы доказательств или семантику безопасности\.

## Пишите для быстрого просмотра и перевода

- Начинайте с результата для читателя и ставьте важные термины в начало заголовков и абзацев\.
- Используйте действительный залог и называйте исполнителя\, ответственного за действие\.
- В описаниях процедур обращайтесь к читателю напрямую\.
- Делайте абзацы короткими и отводите каждому одну задачу\.
- Используйте нумерованные списки для последовательностей и маркированные — для вариантов без заданного порядка\.
- Используйте описательные ссылки вместо общих подписей вроде «нажмите здесь»\.
- Сохраняйте иерархию заголовков\, делайте их конкретными и однотипными на одном уровне\.
- Предпочитайте буквальный\, однозначный язык\, сохраняющий смысл при переводе\.
- Ставьте условия перед инструкциями\, а ожидаемые результаты — после команд\.

## Проверяйте семантику\, а не оформление

Тесты документации должны проверять больше\, чем совпадение заголовков\. Они проверяют\:

- один заголовок H1 и логическая иерархия заголовков\;
- упорядоченные маркеры смысловых разделов и критически важных утверждений\;
- точные команды первого успешного выполнения и стабильные идентификаторы\;
- относительные ссылки и переходы к деталям для конкретной локали\;
- соответствие бейджа версии метаданным времени выполнения\;
- осмысленный alt\-текст для изображений и соседние текстовые альтернативы\;
- единый жизненный цикл Mermaid с полным текстовым эквивалентом\;
- ограничения на двухколоночные таблицы и длину абзацев\;
- отсутствие выделенных глубоких деталей реализации на целевых страницах\;

## Исследовательская основа

- [GitHub\: О файле README репозитория](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes) определяет назначение README при первом посещении и рекомендует переносить объёмную документацию в другие места\.
- [Diátaxis](https://diataxis.fr/start-here/) разделяет потребности в учебных материалах\, практических руководствах\, объяснениях и справочниках\.

- [Стиль документации Google для разработчиков](https://developers.google.com/style/highlights) рекомендует действительный залог\, прямое обращение\, описательные заголовки\, доступность и письмо для международной аудитории\.
- [GitHub\: Создание диаграмм](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams) описывает поддержку Mermaid в Markdown\.
- [W3C WAI\: Учебное руководство по изображениям](https://www.w3.org/WAI/tutorials/images/) требует текстовых альтернатив и полных эквивалентов для информативных и сложных визуальных элементов\.
