[Огляд у 41 локалізованій версії та офіційні точки входу на вебсайтах](../../../docs/LANGUAGES.md)\. Англійська версія залишається визначальним текстом цього редакційного плану\.

README Better Workflows — це цільова сторінка\, а не стислий довідковий посібник\. Її завдання — допомогти читачеві послідовно відповісти на п’ять запитань\:

1. Що це і чи підходить воно мені\?
2. Яку проблему це розв’язує\?
3. Чому я маю довіряти його твердженням\?
4. Який найкоротший шлях до першого успіху\?
5. Куди перейти далі\?

Цей план визначає контракт щодо викладу\, візуальних матеріалів\, локалізації та перевірки для кожного README в репозиторії\. Машиночитане джерело — [`readme-quality-v1.json`](../../../plugins/better-workflows/config/readme-quality-v1.json)\.

## Починайте з рішення читача

GitHub показує README раніше за більшість вмісту репозиторію\. Тому перший екран має визначити обіцянку продукту\, цільову аудиторію та наступну дію з чіткими межами\. Він не повинен починатися з внутрішньої архітектури\, повного довідника команд або подробиць відновлення випуску\.

Пишіть з огляду на такі завдання читачів\:

- **Новий відвідувач\:** швидко зрозуміти\, чи вирішує Better Workflows актуальну проблему\.
- **Новий користувач\:** встановити плагін і досягти одного успішного автоматичного маршруту\.
- **Оцінювач\:** зрозуміти межу повноважень і поведінку за замовчуванням із безпечною відмовою \(fail\-closed\)\.
- **Постійний оператор\:** швидко перейти до відповіді щодо робочого процесу\, безпеки\, архітектури чи CLI\.
- **Контриб\'ютор або перекладач\:** знайти канонічний контракт\, команди для розробки\, підтримку та керування проєктом\.

## Використовуйте причинно\-наслідковий виклад

П’ять цільових README використовують однакову семантичну послідовність із восьми частин\. Заголовки можуть звучати природно кожною мовою\, але шлях читача не змінюється\.

| Розділ | Запитання читача та роль у викладі |
| --- | --- |
| Обіцянка й аудиторія | Що таке Better Workflows\, навіщо він існує і для кого призначений\? |
| Від проблеми до результату | Що йде не так\, коли намір\, повноваження\, докази та результат постачальника змішують\? |
| Підтвердження та межі | Які гарантії роблять запропонований результат достовірним\? |
| Перший успіх | Який найкоротший повний шлях від установлення до результату\? |
| Вибір наступного шляху | Який робочий процес або документ відповідає меті читача\? |
| Життєвий цикл | Як мета перетворюється на завершення\, підтверджене звірянням\, або безпечно зупиняється\? |
| Довіра й обмеження | Чого система ніколи не може припускати\, дозволяти або стверджувати\? |
| Навчання\, допомога\, внесок | Де знайти поглиблену документацію\, підтримку\, управління\, розробку та ліцензію\? |

Такий порядок створює практичну логіку викладу\:

- **Контекст\:** робота\, керована запитами до моделей\, може виражати намір без підтвердження повноважень або стану\.
- **Напруження\:** побічні ефекти перетворюють цю прогалину на ризик отримання результату\.
- **Розв’язання\:** Better Workflows пов’язує мету\, обсяг\, докази\, перевірку\, дію та звіряння з постачальником\.
- **Підтвердження\:** явні гарантії та межі показують\, як працює розв’язання\.
- **Дія\:** читач досягає першого успіху ще до ознайомлення з поглибленими подробицями реалізації\.
- **Продовження\:** маршрути за роллю та результатом спрямовують читача до потрібного навчального матеріалу\, практичної інструкції\, пояснення або довідника\.

## Відокремлюйте цільову сторінку від поглибленої документації

Використовуйте README для інформації\, потрібної для ухвалення рішення\. Спрямовуйте до подробиць відповідно до мети\:

- [Початок роботи](getting-started.md) — навчальний матеріал для першого використання\.
- [Робочі процеси](workflows.md) — практична інструкція з вибору результату\.
- [Архітектура](architecture.md) пояснює площину керування та компроміси\.
- [Безпека](security-guide.md) пояснює повноваження\, приватність\, засвідчення та поведінку\, що блокує виконання без перевірки\.
- [Довідник CLI](cli-reference.md) — довідник команд\.
- Локалізовані сторінки `docs/details/*.md` зберігають повний переклад подробиць\.

Не дублюйте на цільовій сторінці відновлення кешу\, володіння блокуваннями\, повну семантику транспорту постачальників\, вичерпний перелік команд або історію змін реалізації\. Стисле твердження про безпеку залишається на цій сторінці\, а його докладне обґрунтування\, придатне для аудиту\, належить до визначального посібника\.

Цей поділ відповідає розмежуванню Diátaxis між навчальними матеріалами\, практичними інструкціями\, поясненнями та довідниками\. Одна сторінка не може одночасно бути оптимальною для всіх чотирьох потреб читачів\.

## Кожен візуальний матеріал має виправдовувати своє місце

Використовуйте візуальний матеріал лише тоді\, коли він суттєво полегшує розуміння зв’язків\, ієрархії або переходів стану порівняно зі звичайним текстом\.

На цільових сторінках дозволено два візуальні матеріали\:

1. **Архітектура меж повноважень\:** пояснює\, які рівні визначають намір\, поточні факти\, повноваження інструментів\, обмежені повторні спроби та стан лише для читання\.
2. **Життєвий цикл від мети до завершення\:** пояснює\, де перевіряють докази\, де дозволяють побічні ефекти та де невідомий стан зупиняє просування\.

Кожен візуальний матеріал має містити\:

- стислий і змістовний альтернативний текст\;
- розташований поруч текстовий еквівалент\, який зберігає висновок\, коли візуальний матеріал приховано або Mermaid не відображається\;
- справжній текст для основних підписів\, коли це можливо\;
- стале запитання читача\, яке обґрунтовує потребу підтримувати матеріал актуальним\.

Не додавайте декоративні знімки екрана\, зображення з надлишком тексту або діаграму\, що лише дублює короткий список\. Обмежуйте таблиці вибору двома стислими стовпцями\, щоб ними було зручно користуватися на вузьких екранах\.

## Зберігайте зміст усіма мовами

Англійська є семантичним орієнтиром\, а не зразком кількості рядків\. Традиційна китайська\, спрощена китайська\, японська та корейська мають звучати природно для носія мови\, зберігаючи той самий контракт\.

Такі елементи мають залишатися еквівалентними\:

- вісім семантичних розділів та їхній порядок\;
- команди для першого успіху та ідентифікатори продукту\;
- п’ять тверджень про повноваження\, докази\, невідомий стан\, запити до моделей і приватність\;
- сторінки призначення для робочих процесів\, безпеки\, архітектури\, CLI\, підтримки\, управління\, розробки та ліцензії\;
- призначення візуальних матеріалів\, етапи життєвого циклу та резервні текстові пояснення\;
- джерело версії та політика значків\.

Заголовки\, межі речень\, пунктуація\, приклади та заклики до дії можуть відповідати природним мовним нормам\. Ніколи не перекладайте команди\, селектори\, ідентифікатори доказів або семантику безпеки\.

## Пишіть для швидкого перегляду та перекладу

- Починайте з результату для читача й ставте важливі терміни на початку заголовків і абзаців\.
- Використовуйте активний стан і називайте виконавця\, відповідального за дію\.
- У процедурах звертайтеся безпосередньо до читача\.
- Робіть абзаци короткими й відводьте кожному одне завдання\.
- Використовуйте нумеровані списки для послідовностей\, а марковані — для варіантів без визначеного порядку\.
- Використовуйте описові посилання замість загальних підписів на кшталт «натисніть тут»\.
- Заголовки мають бути ієрархічними\, конкретними й однотипними на одному рівні\.
- Віддавайте перевагу буквальній\, однозначній мові\, яка зберігає зміст під час перекладу\.
- Розміщуйте умови перед інструкціями\, а очікувані результати — після команд\.

## Перевіряйте семантику\, а не оформлення

Тести документації мають перевіряти більше\, ніж збіг заголовків\. Вони перевіряють\:

- один H1 та логічна ієрархія заголовків\;
- упорядковані маркери семантичних розділів і критичних тверджень\;
- точні команди першого успішного запуску та стабільні ідентифікатори\;
- відносні посилання та локалізовані кінцеві точки з деталями\;
- відповідність бейджів версій метаданим часу виконання\;
- змістовний alt\-текст зображень і супутні візуальні резервні варіанти\;
- один життєвий цикл Mermaid із повним текстовим еквівалентом\;
- обмеження для таблиць із двох колонок і довжини абзаців\;
- відсутність спеціально виділених глибоких деталей реалізації на цільових сторінках\;
