[ภาพรวมที่ปรับให้เหมาะกับท้องถิ่น 41 ฉบับและช่องทางเข้าสู่เว็บไซต์อย่างเป็นทางการ](../../../docs/LANGUAGES.md) ฉบับภาษาอังกฤษยังคงเป็นฉบับมาตรฐานของพิมพ์เขียวด้านบรรณาธิการนี้

README ของ Better Workflows คือหน้าแนะนำผลิตภัณฑ์ ไม่ใช่คู่มืออ้างอิงที่ถูกย่อรวมไว้ หน้าที่ของมันคือช่วยให้ผู้อ่านตอบคำถามห้าข้อตามลำดับ\:

1. สิ่งนี้คืออะไร และเหมาะกับฉันหรือไม่\?
2. มันแก้ปัญหาอะไร\?
3. เหตุใดฉันจึงควรเชื่อถือคำกล่าวอ้างของมัน\?
4. เส้นทางที่สั้นที่สุดสู่ความสำเร็จครั้งแรกคืออะไร\?
5. ฉันควรไปที่ใดต่อ\?

พิมพ์เขียวนี้กำหนดข้อตกลงด้านการเล่าเรื่อง ภาพประกอบ การปรับให้เหมาะกับแต่ละภาษาและภูมิภาค และการตรวจสอบความถูกต้องสำหรับ README ทุกไฟล์ในที่เก็บโค้ด แหล่งข้อมูลที่เครื่องอ่านได้คือ [`readme-quality-v1.json`](../../../plugins/better-workflows/config/readme-quality-v1.json)

## เริ่มจากการตัดสินใจของผู้อ่าน

GitHub แสดง README ก่อนเนื้อหาส่วนใหญ่ในที่เก็บโค้ด ดังนั้น หน้าจอแรกต้องระบุคำมั่นของผลิตภัณฑ์ กลุ่มเป้าหมาย และการดำเนินการถัดไปที่มีขอบเขตชัดเจน โดยต้องไม่เริ่มด้วยสถาปัตยกรรมภายใน คู่มืออ้างอิงคำสั่งฉบับเต็ม หรือรายละเอียดการกู้คืนรุ่นเผยแพร่

เขียนเพื่อรองรับสิ่งที่ผู้อ่านต้องการทำต่อไปนี้\:

- **ผู้เยี่ยมชมใหม่\:** ตัดสินใจได้อย่างรวดเร็วว่า Better Workflows แก้ไขปัญหาที่เกี่ยวข้อง ได้หรือไม่
- **ผู้ใช้ใหม่\:** ติดตั้งปลั๊กอินและไปถึงเส้นทางอัตโนมัติที่สำเร็จอย่างน้อยหนึ่งเส้นทาง
- **ผู้ประเมิน\:** เข้าใจขอบเขตอำนาจและพฤติกรรมแบบ fail\-closed
- **โอเปอเรเตอร์ที่กลับมาใช้งาน\:** ข้ามไปยังคำตอบเกี่ยวกับเวิร์กโฟลว์\, ความปลอดภัย\, สถาปัตยกรรม หรือ CLI ได้ทันที
- **ผู้ร่วมพัฒนาหรือผู้แปล\:** ค้นหา contract ฉบับทางการ\, คำสั่งในการพัฒนา\, การสนับสนุน และการกำกับดูแล

## ใช้การเล่าเรื่องแบบเหตุและผล

README สำหรับหน้าแนะนำผลิตภัณฑ์ทั้งห้าฉบับใช้ลำดับความหมายแปดส่วนเหมือนกัน หัวข้ออาจใช้สำนวนที่เป็นธรรมชาติของแต่ละภาษาได้ แต่เส้นทางการอ่านไม่เปลี่ยนแปลง

| ส่วน | คำถามของผู้อ่านและบทบาทในการเล่าเรื่อง |
| --- | --- |
| คำมั่นและกลุ่มเป้าหมาย | Better Workflows คืออะไร มีขึ้นเพื่ออะไร และเหมาะกับใคร\? |
| จากปัญหาสู่ผลลัพธ์ | อะไรจะผิดพลาดเมื่อเจตนา อำนาจ หลักฐาน และผลลัพธ์จากผู้ให้บริการถูกปะปนเป็นเรื่องเดียวกัน\? |
| ข้อพิสูจน์และขอบเขต | หลักประกันใดทำให้ผลลัพธ์ที่เสนอมีความน่าเชื่อถือ\? |
| ความสำเร็จครั้งแรก | เส้นทางที่ครบถ้วนและสั้นที่สุดตั้งแต่ติดตั้งจนได้ผลลัพธ์คืออะไร\? |
| เลือกเส้นทางถัดไป | เวิร์กโฟลว์หรือเอกสารใดตรงกับเป้าหมายของผู้อ่าน\? |
| วงจรชีวิต | เป้าหมายกลายเป็นการดำเนินงานที่เสร็จสิ้นและผ่านการตรวจสอบเทียบเคียง หรือหยุดอย่างปลอดภัยได้อย่างไร\? |
| ความเชื่อถือและข้อจำกัด | สิ่งใดบ้างที่ระบบไม่สามารถอนุมาน อนุญาต หรือกล่าวอ้างได้ไม่ว่าในกรณีใด\? |
| เรียนรู้ ขอความช่วยเหลือ ร่วมพัฒนา | เอกสารเชิงลึก การสนับสนุน การกำกับดูแล การพัฒนา และใบอนุญาตอยู่ที่ใด\? |

ลำดับนี้ทำให้เกิดโครงเรื่องที่นำไปใช้ได้จริง\:

- **บริบท\:** งานที่ขับเคลื่อนด้วยพรอมป์ต์สามารถแสดงเจตนาได้โดยไม่พิสูจน์อำนาจ หรือสถานะ
- **ปมปัญหา\:** ผลข้างเคียงทำให้ช่องว่างนั้นกลายเป็นความเสี่ยงต่อการส่งมอบผลลัพธ์
- **ทางแก้\:** Better Workflows เชื่อมเป้าหมาย ขอบเขต หลักฐาน การทบทวน การดำเนินการ และการตรวจสอบเทียบเคียงกับผู้ให้บริการเข้าด้วยกัน
- **ข้อพิสูจน์\:** หลักประกันและขอบเขตที่ชัดเจนแสดงให้เห็นว่าทางแก้ทำงานอย่างไร
- **การลงมือทำ\:** ผู้อ่านบรรลุความสำเร็จครั้งแรกก่อนพบรายละเอียด เชิงลึกของการนำไปพัฒนา
- **การไปต่อ\:** เส้นทางตามบทบาทและผลลัพธ์นำผู้อ่านไปยัง บทเรียน คู่มือปฏิบัติ คำอธิบาย หรือเอกสารอ้างอิงที่เหมาะสม

## แยกเนื้อหาหน้าแนะนำออกจากเอกสารเชิงลึก

ใช้ README สำหรับข้อมูลที่เกี่ยวข้องกับการตัดสินใจ แล้วนำไปสู่รายละเอียดตามวัตถุประสงค์\:

- [เริ่มต้นใช้งาน](getting-started.md) คือบทเรียนสำหรับการใช้งานครั้งแรก
- [เวิร์กโฟลว์](workflows.md) คือคู่มือปฏิบัติสำหรับเลือกผลลัพธ์
- [สถาปัตยกรรม](architecture.md) อธิบายระนาบควบคุมและข้อแลกเปลี่ยน
- [ความมั่นคงปลอดภัย](security-guide.md) อธิบายอำนาจ ความเป็นส่วนตัว คำรับรอง และ พฤติกรรมที่ปฏิเสธการดำเนินการเมื่อยังตรวจสอบยืนยันไม่ได้
- [เอกสารอ้างอิง CLI](cli-reference.md) คือเอกสารอ้างอิงคำสั่ง
- หน้า `docs/details/*.md` ที่ปรับให้เหมาะกับแต่ละภาษาและภูมิภาคเก็บรายละเอียดฉบับแปลไว้อย่างครบถ้วน

อย่าทำซ้ำเนื้อหาเกี่ยวกับการกู้คืนแคช ความเป็นเจ้าของล็อก ความหมายและพฤติกรรมของการรับส่งข้อมูลกับผู้ให้บริการอย่างครบถ้วน รายการคำสั่งทั้งหมด หรือประวัติการเปลี่ยนแปลงการพัฒนาไว้ในหน้าแนะนำ ให้คงคำกล่าวอ้างด้านความปลอดภัยอย่างกระชับไว้ในหน้านั้น ส่วนรายละเอียดเชิงลึกที่ตรวจสอบย้อนหลังได้ต้องอยู่ในคู่มือฉบับมาตรฐาน

การแยกเช่นนี้เป็นไปตามแนวคิด Diátaxis ซึ่งแยกบทเรียน คู่มือปฏิบัติ คำอธิบาย และเอกสารอ้างอิงออกจากกัน หน้าเดียวไม่สามารถตอบสนองความต้องการของผู้อ่านทั้งสี่แบบได้อย่างเหมาะสมที่สุดพร้อมกัน

## ภาพประกอบทุกชิ้นต้องมีเหตุผลรองรับ

ใช้ภาพประกอบเฉพาะเมื่อช่วยให้เข้าใจความสัมพันธ์ ลำดับชั้น หรือการเปลี่ยนสถานะได้ง่ายกว่าข้อความอย่างมีนัยสำคัญ

หน้าแนะนำอนุญาตให้มีภาพประกอบสองชิ้น\:

1. **สถาปัตยกรรมขอบเขตอำนาจ\:** อธิบายว่าชั้นใดกำหนดเจตนา ข้อเท็จจริงปัจจุบัน อำนาจของเครื่องมือ การลองใหม่ที่มีขอบเขต และสถานะที่อ่านได้อย่างเดียว
2. **วงจรจากเป้าหมายจนเสร็จสิ้น\:** อธิบายว่าตรวจสอบหลักฐานที่ใด อนุญาต ผลข้างเคียงที่ใด และสถานะที่ยังไม่ทราบทำให้ความคืบหน้าหยุดลงที่ใด

ภาพประกอบทุกชิ้นต้องมี\:

- ข้อความทดแทนที่กระชับและสื่อความหมาย\;
- ข้อความเทียบเท่าที่อยู่ติดกันและยังคงข้อสรุปไว้เมื่อซ่อนภาพประกอบ หรือ Mermaid ไม่แสดงผล\;
- ข้อความจริงสำหรับป้ายกำกับสำคัญเมื่อทำได้\;
- คำถามของผู้อ่านที่ยังคงใช้ได้ในระยะยาวและเป็นเหตุผลให้ต้องปรับภาพประกอบให้เป็นปัจจุบัน

อย่าเพิ่มภาพหน้าจอเพื่อการตกแต่ง ภาพที่มีข้อความหนาแน่น หรือแผนภาพที่เพียงทำซ้ำรายการสั้น ๆ ให้ตารางตัวเลือกมีสองคอลัมน์ที่กระชับ เพื่อให้ยังใช้งานได้บนหน้าจอแคบ

## รักษาความหมายให้ตรงกันข้ามภาษา

ภาษาอังกฤษเป็นแหล่งอ้างอิงด้านความหมาย ไม่ใช่เป้าหมายด้านจำนวนบรรทัด ภาษาจีนตัวเต็ม ภาษาจีนตัวย่อ ภาษาญี่ปุ่น และภาษาเกาหลีควรอ่านเป็นธรรมชาติสำหรับเจ้าของภาษา ขณะเดียวกันก็รักษาข้อตกลงเดียวกันไว้

รายการต่อไปนี้ต้องมีความหมายเทียบเท่ากัน\:

- ส่วนเนื้อหาตามความหมายทั้งแปดส่วนและลำดับของส่วนเหล่านั้น\;
- คำสั่งสำหรับความสำเร็จครั้งแรกและตัวระบุผลิตภัณฑ์\;
- คำกล่าวอ้างห้าข้อเกี่ยวกับอำนาจ หลักฐาน สถานะที่ยังไม่ทราบ พรอมป์ต์ และความเป็นส่วนตัว\;
- ปลายทางเกี่ยวกับเวิร์กโฟลว์ ความมั่นคงปลอดภัย สถาปัตยกรรม CLI การสนับสนุน การกำกับดูแล การพัฒนา และ ใบอนุญาต\;
- วัตถุประสงค์ของภาพประกอบ ขั้นตอนในวงจรชีวิต และข้อความสำรอง\;
- แหล่งที่มาของเวอร์ชันและนโยบายป้ายสถานะ

หัวข้อ การแบ่งประโยค เครื่องหมายวรรคตอน ตัวอย่าง และข้อความชวนให้ลงมือทำอาจปรับให้เป็นธรรมชาติตามภาษาได้ ห้ามแปลคำสั่ง ตัวเลือก ตัวระบุหลักฐาน หรือความหมายเชิงความมั่นคงปลอดภัย

## เขียนให้อ่านกวาดสายตาและแปลได้ง่าย

- เริ่มด้วยผลลัพธ์ที่ผู้อ่านจะได้รับ และวางคำสำคัญไว้ตอนต้นของ หัวข้อและย่อหน้า
- ใช้ประโยคที่ระบุผู้กระทำและบอกว่าใครเป็นผู้รับผิดชอบการดำเนินการ
- กล่าวกับผู้อ่านโดยตรงเมื่ออธิบายขั้นตอนปฏิบัติ
- เขียนย่อหน้าให้สั้นและให้แต่ละย่อหน้าทำหน้าที่เพียงอย่างเดียว
- ใช้รายการลำดับเลขสำหรับขั้นตอนตามลำดับ และใช้รายการหัวข้อย่อยสำหรับตัวเลือกที่ไม่ต้องเรียงลำดับ
- ใช้ข้อความลิงก์ที่บอกปลายทาง แทนข้อความทั่วไปอย่าง “คลิกที่นี่”
- จัดหัวข้อให้มีลำดับชั้น เฉพาะเจาะจง และมีรูปแบบคู่ขนานกันเมื่ออยู่ในระดับเดียวกัน
- เลือกใช้ภาษาตรงความหมาย ไม่กำกวม และยังคงความหมายเมื่อแปล
- วางเงื่อนไขไว้ก่อนคำแนะนำ และวางผลลัพธ์ที่คาดหวังไว้หลังคำสั่ง

## ตรวจสอบความหมาย ไม่ใช่การตกแต่ง

การทดสอบเอกสารต้องตรวจพบได้มากกว่าการที่หัวข้อตรงกัน โดยตรวจสอบ\:

- H1 หนึ่งรายการและลำดับชั้นหัวข้อที่สมเหตุสมผล\;
- มาร์กเกอร์เซกชันเชิงความหมายและข้ออ้างสำคัญที่จัดลำดับไว้\;
- คำสั่งสู่ความสำเร็จครั้งแรกที่แม่นยำและตัวระบุที่เสถียร\;
- ลิงก์แบบสัมพัทธ์และปลายทางรายละเอียดเฉพาะแต่ละภาษา\;
- ความสอดคล้องของแบดจ์เวอร์ชันกับเมทาดาตารันไทม์\;
- ข้อความ alt ของรูปภาพที่มีความหมายและ fallback แบบภาพที่อยู่ติดกัน\;
- วงจรชีวิต Mermaid รายการเดียวพร้อมข้อความเทียบเท่าที่สมบูรณ์\;
- ตารางสองคอลัมน์และงบความยาวของย่อหน้า\;
- ปราศจากรายละเอียดการนำไปใช้เชิงลึกที่ระบุไว้ในหน้า landing page\;
